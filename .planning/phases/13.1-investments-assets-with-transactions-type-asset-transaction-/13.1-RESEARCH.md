## Summary

Phase 13 already built ~70% of the engine: `budgeting.investment_history` is a delta ledger (qty/cost/value deltas, flow, realized, `transfer_id` linking two legs, soft delete), `sell-booking.ts` has the proportional/average-cost math, and `planLegUndo` already reverses both legs. The holding row (`budgeting.investments`) already stores **aggregate state** (`quantity`, average `buy_price_cents`, `current_price_cents`). That row IS an asset: the three-level model needs no new table. Every other consumer (hourly price worker joins `investments.instrument_id`, daily snapshot job, `compute-budget-wealth-now` valuation port, Overview contributions via `listFlows`, `realizedByType`, tenant-leak tests, demo manifest, account deletion cascade) keeps working untouched if the asset row stays in `budgeting.investments`.

What changes: (1) migration 0088 merges same name+type rows into one and enforces uniqueness of (budget, ui_type, label); (2) new entry kinds (`transfer_out/in`, `price_change`) and wallet-link columns on the ledger; (3) a strict **LIFO + monotone-date** invariant (D-14/D-15) that actually _removes_ the Phase 13 reversal hazards (CR-04) because snapshot-style undo becomes safe; (4) new/reshaped use cases (buy-into-asset, asset sell with wallet target, transfer, delete-newest-entry, edit label/currency) replacing `adjust`, per-entry `DELETE /history/:id`, `PATCH` cost writes and `deleteHolding`; (5) the web layer: L1/L2/L3 list, Swap sheet, Edit sheet, autocomplete.

The two genuinely new risks are the **data-merge migration** (dev DB: 160 holdings, 23 same-name groups, 2 with mixed buy currency, 9 with mixed/NULL instrument, 3 mixing archived+active; real RLS data-loss precedent) and the **cross-context wallet write** (must be atomic with the sale, must still fire RESERVE/CUSHION task recomputes).

**Primary recommendation:** Keep `budgeting.investments` as the asset table, evolve `investment_history` into the entry ledger via additive migration 0088 (+ merge), implement LIFO as "max by (effective_date, created_at, id)" under a `SELECT ... FOR UPDATE` on the asset row(s), and do the wallet credit as raw SQL inside `HistoryRepo.commit()`'s transaction (plus audit), with the API composition root running RESERVE/CUSHION recompute hooks after commit.

### Ledger invariants (make the rules mechanical)

- **Newest entry** := last live row by `(effective_date, created_at, id)`. With D-15 (new date >= latest date) this equals "most recently created" for all new data, and it gives a defined answer for migrated data whose creation order != date order. One rule, used by delete, by the date-picker `min`, and by the linked-leg check.
- Interest rows are synthesized, never in this table, so they never participate in "newest".
- Because deletion is strictly LIFO, **snapshot undo is now safe** (prior principal/start date for deposit sales; prior price for `price_change`). Delta undo stays for qty/cost/value. This is what dissolves CR-04.
- A legs pair (`transfer_id`) is deletable iff each leg is the newest live entry of its own asset. Check in the same tx as the delete.
- After reversal, if the asset has **zero live entries** -> hard-delete the asset row (D-17 wipe; FK cascade removes history and so realized). Else if qty after reversal > 0 -> `archived_at = NULL`; qty = 0 -> `archived_at = now()` (hidden).
- Concurrency: `commit()` must `SELECT ... FOR UPDATE` the asset row(s) first, then re-verify the preconditions (newest entry id / max date / quantity) inside the tx. Plans should carry `expectedNewestEntryId` from the read so a stale delete fails with 409 rather than undoing the wrong row. (The `ponytail:` note in reverse-history-entry.ts deferred this; D-15/D-16 make it correctness-critical.)

## Migration 0088 (highest-risk task)

Facts from the dev DB (read-only counts, 2026-10-27) `[VERIFIED: psql]`: 160 `investments` rows in 12 budgets (77 active, 83 archived, 15 active with NULL buy price), 0 possessions left. 23 same (budget, ui_type, lower(name)) groups: crypto 16, precious_metals 3, cash 2, stocks 1, real_estate 1. Of those: 2 groups mix buy currencies, 9 mix instrument (incl. NULL vs set), 3 mix archived+active.

### Merge algorithm (per group; survivor = oldest non-archived else oldest row)

- Re-point all `investment_history.holding_id` to the survivor; `UPDATE` survivor with Σ quantity (active rows only; archived rows were sold out/hidden: their history is kept, their remaining qty is not added), cost = Σ(buy_price_cents x quantity) / Σquantity for qty assets, Σ buy_price for amount assets (qty=1), Σ current value for amount assets; delete the emptied rows only after the repoint UPDATE row count is verified.
- **Conflicts** (mixed buy currency, mixed instrument, deposit with different rate/dates, mixed hand-priced currencies): do NOT silently merge. Rename the minority rows deterministically (`"<name> (<CCY>)"` / `"<name> (2)"`) so the unique index holds and no data is lost; `RAISE NOTICE` the count. `[ASSUMED]` policy (A1) — the user said "same name + type merge", but a mixed-currency average cost cannot be computed without an FX source in SQL. Surface the choice at plan time / checkpoint.
- **Archived holdings:** an archived row with live history merges into/stays with its group but stays hidden if the group has no active qty. 0087 gave Start entries only to ACTIVE priced rows, so 15 active NULL-buy rows and all archived rows have no entries: backfill a `start` entry (cost 0) so an asset never has an empty L3 (otherwise D-17 "wipe when no entries" would fire wrongly on first delete). Decide rule in plan; test with fixtures.
- Entries from merged holdings interleave by date but their `created_at` order differs; the newest rule above handles it. Two legs of one `transfer_id` that now live in the same asset: leave as is (net zero) — document, test.
- Idempotent (`IF NOT EXISTS`, `WHERE NOT EXISTS`), mirroring 0087.

### Mandatory safety rules (from the 260803 incident, memory `project_migration_rls_data_loss`) `[VERIFIED: memory + 0087 header]`

1. `ALTER TABLE ... NO FORCE ROW LEVEL SECURITY` on **every** table the statements touch **including JOIN/subquery tables** (`budgeting.investments`, `budgeting.investment_history`, and `tenancy.budgets`/`budgeting.wallets` if joined). Migrator has no BYPASSRLS; an unseeable join silently matches 0 rows. `post-migration.sql` re-applies FORCE; restore at end of file like 0087 does.
2. Every DELETE conditional on the INSERT/UPDATE having landed (`DELETE ... WHERE EXISTS (SELECT 1 FROM survivor ...)`).
3. Backups: `CREATE TABLE IF NOT EXISTS bak (LIKE ...)` then `INSERT ... SELECT ... WHERE NOT EXISTS`; never `CREATE TABLE IF NOT EXISTS ... AS SELECT`.
4. Dump affected rows to a file before running on dev (dev holds the user's real data).
5. Migration test (`apps/api/test/schema/` like `investment-history-0087.test.ts`): seed a pre-0088 shape, run the SQL, assert row counts (investments before - merged = after; history count unchanged; Σ qty and Σ cost per group preserved; unique index holds). `make migrate` no-ops on a stale image — rebuild migrator (`project_migrator_and_cigate_docker`). Needs `infisical run` for DB tests.

## Sell-to-wallet design (D-20..D-25)

Facts `[VERIFIED: codebase]`: `budgeting.wallets` has `currency char(3)`, `current_balance numeric(19,4)` (major units, decimal), `wallet_type` CHECK incl. 2. Store `wallet_id`, `wallet_delta_numeric`, `wallet_created` on the `withdraw` entry. Reversal: `current_balance = current_balance - wallet_delta` (D-21 delta even if balance since edited; wallet row missing/`ON DELETE SET NULL` -> skip, never fail the undo; D-24 never delete the wallet).
3. Cents -> major: bigint cents / 100 via string/Big (no float). Verify the app's existing helper for 0-decimal currencies (JPY) before assuming /100 — `[ASSUMED]` A6.

Raw SQL skips them. 5. Web: invalidate wallets caches (`["budget", id, "wallets"]`-family) + investments + type-summary + overview + reserves/cushion on a wallet-targeted sale and on its delete.

## Derived math

- Asset state is stored and updated by deltas; displayed cost = `buy_price x qty`. **Pitfall:** `buy_price_cents` is a rounded integer per unit (`cents(total/newQty)`), so cost drifts <= qty/2 cents on large unit counts. Phase 13 behaviour; D-14 "delta model holds" keeps it. Mitigation to plan: a property test that Σ entry deltas == asset state within 1 cent x ceil(qty), and compute P/L, "cost" and the broker preview from Σ ledger where exactness matters. Do not widen the column.

### Pattern: BookingPlan under lock

Read assets (no lock) → pure plan → `commit()` locks `lockHoldingIds` (`SELECT id FROM budgeting.investments WHERE id = ANY(...) ORDER BY id FOR UPDATE`, ordered to avoid deadlocks), re-reads newest entry id/qty, aborts with `stale` (409) if it differs from the plan's expectation. Drizzle array binding: use `sql.join` of uuids in `IN (...)`, never `ANY($1)` with a JS array (memory `feedback_drizzle_sql_template_array_expansion`).

### Anti-Patterns

- A second PATCH path that writes cost/qty (the T6 race). The SQL UPDATE must not contain ledger-owned columns.
- Computing `deletable` on the client. Server returns it with a reason code.
- Storing interest rows. Synthesized only.
- Adding Drizzle imports to domain; Money conversion inside domain adapters boundary rule stays.

## Common Pitfalls

1. **Merge migration silently loses data** (RLS on JOINed table). See safety rules above. Warning sign: row counts after != expected; test asserts conservation of Σqty, Σcost, history count.
2. **Mixed-currency / mixed-instrument merge** produces a meaningless average. Rename-not-merge policy + NOTICE; checkpoint with user.
3. **LIFO off by creation vs date.** Use the single `(effective_date, created_at, id)` rule everywhere, server-side.
4. **Stale concurrent delete/buy** (two tabs/PWA). Row lock + expected-newest check -> 409.
5. **Sold-out asset revival**: buy under a hidden label must `unarchive` and keep history (D-17); unique index prevents creating a duplicate row. Autocomplete must include `archived_at IS NOT NULL`.
6. **Delete removing the last entry** must hard-delete the asset (cascade). Not a soft archive. UI dialog warns (UI-SPEC).
7. **`withTenantTx` returns a Result**: DB-free tests silently no-op behind it (`feedback_withtenanttx_returns_result`). Integration tests need real Postgres via `infisical run`.
8. **Zod `.partial()` keeps `.default()`**: PATCH body re-declares defaulted keys optional (`feedback_zod_partial_keeps_default`) or label-only edits write quantity=1.
9. **bigint**: `c.json()` throws on bigint; serialize cents as strings; bind bigint as strings; validate `^\d+$` before `BigInt()` (SyntaxError is not RangeError -> 500; Phase 13 WR-01).
10. **Wallet delta vs RESERVE/CUSHION recompute** (above). Also invalidate wallets cache or the balance looks stale.
11. **Docker**: web/api/worker/migrator run prebuilt images; rebuild all four after changes; verify the served bundle; i18n JSON bundled at build time (EN/PL/UK keys for every new string; `investments-phase13-keys.test.ts` style key test).
12. **iOS/WebKit**: new sheets/tap-expand rows hit known traps — `filter` breaks backface, line-clamp nested flex, Radix close-refocus `:focus-visible` (use `onCloseAutoFocus preventDefault`), `hourCycle: "h23"`, sticky bands overlapping top-edge pixels. Playwright-verify on phone viewport + all 3 locales.
13. **Tailwind**: colour via inline style / `--surface-*` tokens, never glued `${}` classes, never hardcoded hex (light theme).
14. **New dnd-kit scope**: L2 reorder is a nested SortableContext inside a type block; collision detection must keep assets within their type (D-30). dnd-kit discards synthetic drops in E2E (confirm row landed, don't wait longer); keyboard-only DnD pattern exists.
15. **Consumers enumerating investment columns**: `packages/platform/src/demo/manifest.ts`, `packages/identity/.../better-auth.ts` (deletion cascade, Phase 10-06 table list), `scripts/provision-uat-investments.ts`, `apps/web/e2e/fixtures/cleanup-fixture-data.ts`, `apps/worker/test/_investment-fixtures.ts`. No new table, but any that list history columns or rely on duplicate names must be re-checked (duplicate labels now violate the unique index in seeds/fixtures).
