<interfaces>
REVERSAL RULE (D-06, stated once): deleting an entry undoes ONLY that entry, by subtracting its own stored deltas (qty_delta, cost_delta_cents, value_delta_cents) from the holding's CURRENT state via reverseEntry (13-01). Later entries survive untouched. Exceptions, each explicit:
  - deposit sale rows (prior_principal_cents not null): the restart is not delta-expressible, so the prior principal + deposit_start_date are restored — allowed only when that row is the deposit's latest live entry, else 422 undo_later_first
  - a conversion's legs are undone together (both rows found by transfer_id); a convert_in leg whose holding has no OTHER live entry was created by that conversion -> the holding is hard-deleted instead of reduced
  - undoing a withdraw/convert_out on an archived (sold-completely) holding un-archives it
  - reverseEntry RangeError would_empty_holding / would_go_negative -> 422 with that code (UI copy history.errWouldEmpty)
  - every undone row gets deleted_at = now() (soft delete; reads filter it), so realized (type summary) and contributions (listFlows) reverse automatically; re-entering creates fresh rows — no double count
  - all patches + soft deletes + holding deletes run in ONE commit (BookingPlan gains softDeleteEntryIds?: string[]; deleteHoldingIds?: string[]). ponytail: read-then-commit is not serializable; fine for a household, add SELECT ... FOR UPDATE if concurrent edits ever matter
