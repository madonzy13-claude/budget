Config (`packages/platform/src/demo/config.ts`). Currency and scale are **per pair**, not global:

```ts
export type DemoPair = {
  source: string;
  dest: string;
  label: "personal" | "family";
  currency: string; // dest budget default_currency
  currencyMap: Record<string, string>; // {} = keep source currencies as-is
  moneyScale: number;
};
export type DemoConfig = { pairs: DemoPair[]; demoUserId: string };
export function readDemoConfig(env = process.env): DemoConfig | null; // null when unconfigured
```

`null` means "do not schedule" — the inert-by-default guarantee. Do not throw on missing config; an unconfigured prod deploy is a valid state.

Source → dest pairing (from 12-CONTEXT; ids live in Infisical, not code):

- `d30ee8ca-a44f-493b-af60-0f9cbd9199f8` (Private Budget) → demo **personal**, `currency: "USD"`, `currencyMap: {PLN:"USD"}`, `moneyScale ≈ 0.25`
- `a2372ac5-bcdd-4e70-a4ca-4ab26d1f3bf0` (Family Budget) → demo **family**, `currency: "PLN"`, `currencyMap: {}`, `moneyScale ≈ 0.9`

The two demo budgets deliberately sit in DIFFERENT base currencies so the all-budgets aggregate exercises FX rather than summing like-for-like. That makes the aggregate depend on a PLN→USD `fx_rates` row: production gets it from the daily `fx-daily-fetch` job, and any test touching the aggregate must seed `fx_rates` as the worker role at the exact UTC date (project memory — otherwise the FX cache reaches a live API).

RLS: worker role has NO BYPASSRLS. Inside the job transaction, `SET LOCAL app.tenant_ids = '{<source>,<dest>}'` to make both visible — this is the standard bootstrap pattern used by `withBootstrapUserContext`. `SET LOCAL` means it dies with the transaction.

Wipe order: reuse the delete ordering from `purgeUserData` in `packages/identity/src/adapters/persistence/better-auth.ts`. It already encodes the FK constraints — notably `category_reserve_adjustments` must be deleted BEFORE `categories` (FK NO ACTION). Do not re-derive this order from the schema.

Copy strategy per table:

1. Build an id map for the table's PK: `SELECT id, gen_random_uuid() AS new_id FROM <t> WHERE tenant_id = :source` materialized into a temp table / CTE keyed per source table.
2. `INSERT INTO <t> (cols…) SELECT <rule-applied expressions> FROM <t> src JOIN idmap …` — FK columns join their referenced table's map via `Rule.references`.
3. Iterate tables in FK-safe insert order (reverse of the wipe order).

Aggregate/derived tables: do NOT copy `spending_by_category_month` or `spending_projection` scaled — per-row rounding drifts from the sum of the scaled rows they summarize. Let the existing hourly `budgeting-reconciliation` job rebuild them, or invoke that rebuild at the end of the copy transaction. `budget_wealth_snapshots` IS copied scaled (a time series with no cross-row sum invariant).

pg-boss registration lives in `apps/worker/src/worker.ts` alongside the existing `boss.schedule(...)` calls (`fx-daily-fetch`, `budget-reminder`, `investment-snapshot-daily`, …). Match their 5-field cron format and `{ tz: "UTC" }` option shape.

Deployment gotcha (project memory — the stale-worker incident): worker runs from a prebuilt image. After changing handler code, `make build-worker` AND force-recreate; a plain restart reruns the OLD code and looks like the job silently doing nothing.
